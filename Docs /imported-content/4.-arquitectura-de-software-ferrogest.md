# 4. Arquitectura de software ferroGest

**Ana Lucia Bermudez Rodríguez - Aldair Caicedo Ramos - Samuel Cuervo Rojas - Kevin Andres Puentes Mera**

**Sistema de información web para la gestión de ventas e inventarios de ferreterías con asistente de IA**

## Introducción

Este documento explica qué es la arquitectura de software, describe el patrón modelo vista controlador (MVC) y justifica por qué se utiliza en FerroGest, un sistema de información web para la gestión de ventas e inventario de una ferretería. Al final se muestra un ejemplo de cómo se aplicaría con uno de los módulos del software.

## La arquitectura de software

La arquitectura de software de un sistema es la estructura, o conjunto de estructuras, del sistema. Comprende sus componentes, las propiedades de esos componentes que son visibles desde el exterior y las relaciones que hay entre ellos.

La arquitectura no es el software en funcionamiento, sino una representación de este. Sirve para tres cosas: analizar si el diseño cumple los requisitos establecidos, considerar alternativas de organización en una etapa en la que todavía es fácil cambiar el diseño y reducir los riesgos asociados con la construcción del software.

Para organizar los componentes se suelen emplear patrones de arquitectura, que son soluciones reconocidas y reutilizables a problemas de diseño frecuentes. Uno de los más usados en aplicaciones web es el patrón MVC.

## El patrón MVC

### Definición

MVC es un patrón de arquitectura de software que separa, mediante tres componentes, la lógica de la aplicación de la lógica de presentación. Se emplea desde componentes gráficos básicos hasta sistemas empresariales, y la mayoría de los frameworks modernos lo utilizan o usan una adaptación suya.

| **Componente**  | **Qué hace**                                                                                                                                          |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Modelo**      | Representa los datos y las reglas del negocio, accede a la base de datos y desconoce cómo se muestra la información al usuario.                       |
| **Vista**       | Presenta la información al usuario y captura sus acciones como los clics o formularios, no contiene reglas del negocio.                               |
| **Controlador** | Es el intermediario, recibe las acciones del usuario, las valida, pide al modelo que realice la operación y decide qué respuesta devolver a la vista. |

### Funcionamiento

El usuario interactúa con la vista, esta envía la acción al controlador, el controlador solicita la operación al modelo, el modelo ejecuta la lógica y actualiza los datos, y el resultado regresa por el controlador hasta la vista, que se actualiza para mostrarlo.

## ¿Por qué usamos MVC?

1. **Separación de responsabilidades:** La interfaz, las reglas del negocio y el acceso a datos quedan en capas distintas. Así, un cambio en una pantalla no obliga a modificar el cálculo del IVA ni las consultas a la base de datos.
2. **Trabajo en paralelo:** El equipo es de cuatro personas con roles distintos. Quien diseña y programa las vistas puede avanzar sin esperar a quien programa los controladores y los modelos.
3. **Facilidad de los test:** Las reglas del negocio viven en el modelo y se pueden probar con pruebas unitarias sin necesidad de la interfaz, lo que facilita el trabajo del tester.
4. **Seguridad:** Los controladores verifican el token de sesión, el rol del usuario y los datos recibidos antes de llegar al modelo, de modo que el control de acceso por rol queda centralizado.
5. **Reutilización:** Varias pantallas pueden usar el mismo modelo. Por ejemplo, el dashboard y el asistente de IA consultan las mismas ventas y existencias a través del modelo, sin duplicar lógica.
6. **Coherencia:** MVC encaja con el backend monolítico modular de FerroGest, que se organiza en modelos, controladores y rutas.

## Cómo se aplicará

En FerroGest la interfaz está separada del servidor. La vista es la aplicación React que corre en el navegador, y el backend en Node.js implementa el modelo y el controlador.

La vista y el controlador se comunican mediante peticiones HTTPS con datos en formato JSON. Es una adaptación habitual del patrón en aplicaciones web modernas.

## Ejemplo

{% stepper %}
{% step %}
### El vendedor completa el formulario

El vendedor completa el formulario en la pantalla Registrar venta, que es la **vista**, y confirma.
{% endstep %}

{% step %}
### La vista envía la petición

La vista envía una petición POST ventas con los datos en JSON y el token de sesión.
{% endstep %}

{% step %}
### El controlador valida la solicitud

El **controlador** verifica el token, comprueba que el rol sea vendedor o administrador y valida los datos recibidos.
{% endstep %}

{% step %}
### El controlador solicita la creación de la venta

El controlador pide al **modelo** que cree la venta.
{% endstep %}

{% step %}
### El modelo procesa la venta

El modelo, dentro de una transacción de MySQL, verifica las existencias, calcula subtotal, descuento, IVA y total, guarda la venta y su detalle, descuenta el stock y registra los movimientos de inventario.
{% endstep %}

{% step %}
### Se confirma o revierte la transacción

Si todo sale bien, confirma la transacción. Si algo falla, la revierte y no se guarda nada.
{% endstep %}

{% step %}
### El controlador responde a la vista

El controlador responde a la vista con el resultado con un código 201 y los datos de la venta, o un mensaje de error.
{% endstep %}

{% step %}
### La vista muestra el resultado

La vista muestra la confirmación y permite descargar la factura simulada.
{% endstep %}
{% endstepper %}

### Ventajas

* Cambios localizados: modificar una pantalla, una regla o una consulta afecta solo a su componente.
* Pruebas más sencillas de las reglas del negocio, sin depender de la interfaz.
* Trabajo en paralelo de los integrantes del equipo.
* Reutilización de la misma lógica en varias pantallas y en el asistente de IA.

## Conclusión

El patrón MVC permite organizar FerroGest en tres componentes con responsabilidades claras: la vista en React, y el controlador y el modelo en el backend de Node.js.

Esta separación facilita el trabajo en equipo, las pruebas y el mantenimiento, centraliza la seguridad en el controlador y deja las reglas del negocio en el modelo. Además, cumple el requisito de la asignatura y es coherente con la arquitectura monolítica modular elegida para el sistema.
