Sistema de información web para la gestión de ventas e inventarios de ferreterías con asistente de IA.

## Introducción

Describiremos cómo se gestionarán los datos en FerroGest y cómo se estructura su base de datos. Primero se presentan los conceptos de arquitectura de datos y de diseño de bases de datos; después se describe la arquitectura de datos del sistema, incluyendo las necesidades de datos, flujo, volumen y seguridad; y, por último, se presenta el diseño de la base de datos MySQL, el modelo entidad relación, el diccionario de datos y las decisiones de diseño.

## Conceptos

### Arquitectura de datos

La arquitectura de datos describe cómo se gestionan los datos, desde su recopilación hasta su transformación, distribución y consumo, y establece cómo fluyen a través de los sistemas de almacenamiento. Sus metas son identificar los requerimientos de almacenamiento y procesamiento de datos, diseñar estructuras que respondan a las necesidades presentes y futuras, y preparar a la organización para evolucionar sus productos y servicios apoyándose en los datos.

### Diseño de base de datos

El diseño de una base de datos representa su estructura, describe las entidades, sus relaciones y las restricciones entre ellas, para que se vea cómo se conectan. El proceso consiste en definir la estructura lógica y física de la base de datos para responder a las necesidades de información de los usuarios, decidiendo las tablas y relaciones, los atributos, y las claves primarias y foráneas de cada tabla.

Lo primero en este proceso es la recogida y análisis de requisitos, que consiste en conocer en detalle las necesidades, expectativas y objetivos de los futuros usuarios de la base de datos. En nuestro software esa fase corresponde a la especificación de requisitos de software (ERS).

## Arquitectura de datos

### Necesidades de los datos

| **Datos**                     | **Información principal**                                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Usuarios y roles              | Nombre, correo, contraseña hasheada, rol y estado.                                                                                          |
| Recuperación de contraseña    | Token temporal, fecha de vencimiento y si ya se usó.                                                                                        |
| Categorías y productos        | Código, nombre, categoría, unidad de medida, precios, IVA, stock mínimo, existencias y estado.                                              |
| Movimientos de inventario     | Producto, tipo de movimiento, cantidad, existencias resultantes, nota, fecha y usuario.                                                     |
| Clientes                      | Tipo, nombre, documento, teléfono, correo, dirección y estado.                                                                              |
| Ventas y su detalle           | Cliente, vendedor, número, fecha, medio de pago, totales, estado y motivo de anulación, productos, cantidades, precios e IVA de cada venta. |
| Consultas del asistente de IA | No tiene tablas propias, lee los datos existentes mediante funciones predefinidas del backend.                                              |

## Validación y transformación

El backend verifica el token de sesión y el rol, valida los datos recibidos y los transforma cuando es necesario, calcula subtotal, descuento, IVA y total de una venta, y actualiza las existencias.
{% endstep %}

{% step %}
## Almacenamiento

Los datos se guardan en una base de datos relacional MySQL. Las operaciones que modifican varios registros, como una venta, se ejecutan como una sola transacción.
{% endstep %}

{% step %}
## Distribución y consumo

Los datos se consumen en las pantallas del sistema, en el dashboard, en la factura simulada y en las respuestas del asistente de IA. Para el asistente, el backend consulta primero los datos que el rol del usuario puede ver y solo entonces los envía al modelo de IA para que redacte la respuesta.
{% endstep %}
{% endstepper %}

### Volumen de los datos

* Hasta 5.000 productos y 2.000 clientes registrados, y unas decenas de usuarios.
* Hasta 100 ventas diarias, es decir, hasta unas 36.000 ventas al año, cada una con varias líneas de detalle y sus movimientos de inventario.
* Hasta 3 usuarios conectados al mismo tiempo.
* Uso con predominio de consultas como búsquedas, listados y dashboard, y escritura moderada de ventas y movimientos de inventario.

### Seguridad

* **Acceso por rol:** Cada rol accede solo a los datos que le corresponden.
* **Contraseñas y tokens:** Las contraseñas se guardan como hash y los tokens de recuperación también, con fecha de vencimiento.
* **Comunicación cifrada:** Los datos viajan entre el navegador y el servidor por HTTPS.
* **Integridad:** Las claves foráneas, las restricciones y las transacciones evitan datos inconsistentes, como existencias negativas o ventas sin detalle.

### Modelo Entidad Relación

### Tabla: `rol`

| **Campo** | **Tipo**    | **Clave / Restricción** | **Descripción**                                                            |
| --------- | ----------- | ----------------------- | -------------------------------------------------------------------------- |
| id\_rol   | INT         | PK, AUTO\_INCREMENT     | Identificador único del rol.                                               |
| nombre    | VARCHAR(30) | NOT NULL, UNIQUE        | Nombre del rol (Administrador, Vendedor/Cajero, Encargado del Inventario). |

### Tabla: `usuario`

| **Campo**        | **Tipo**     | **Clave / Restricción** | **Descripción**                                                 |
| ---------------- | ------------ | ----------------------- | --------------------------------------------------------------- |
| id\_usuario      | INT          | PK, AUTO\_INCREMENT     | Identificador único del usuario.                                |
| id\_rol          | INT          | FK → rol                | Rol asignado al usuario.                                        |
| nombre\_completo | VARCHAR(100) | NOT NULL                | Nombre y apellido del usuario.                                  |
| correo           | VARCHAR(100) | NOT NULL, UNIQUE        | Correo electrónico utilizado para la autenticación.             |
| contrasena\_hash | VARCHAR(255) | NOT NULL                | Hash de bcrypt de la contraseña.                                |
| activo           | BOOLEAN      | NOT NULL DEFAULT TRUE   | Estado de la cuenta (permite inicio de sesión si es verdadero). |

### Tabla: `token_recuperacion`

| **Campo**   | **Tipo**     | **Clave / Restricción** | **Descripción**                            |
| ----------- | ------------ | ----------------------- | ------------------------------------------ |
| id\_token   | INT          | PK, AUTO\_INCREMENT     | Identificador del token.                   |
| id\_usuario | INT          | FK → usuario (CASCADE)  | Usuario asociado a la recuperación.        |
| token\_hash | VARCHAR(255) | NOT NULL                | Hash del token de recuperación enviado.    |
| expira\_en  | DATETIME     | NOT NULL                | Fecha y hora límite de validez del token.  |
| usado       | BOOLEAN      | NOT NULL DEFAULT FALSE  | Indicador de si el token ya fue utilizado. |

### Tabla: `cliente`

| **Campo**             | **Tipo**     | **Clave / Restricción** | **Descripción**                                     |
| --------------------- | ------------ | ----------------------- | --------------------------------------------------- |
| id\_cliente           | INT          | PK, AUTO\_INCREMENT     | Identificador único del cliente.                    |
| tipo                  | ENUM         | NOT NULL                | Tipo de cliente (`persona_natural`, `empresa`).     |
| tipo\_documento       | ENUM         | NOT NULL                | Tipo de documento (`CC`, `CE`, `NIT`, `PASAPORTE`). |
| nombre\_razon\_social | VARCHAR(100) | NOT NULL                | Nombre completo o razón social del cliente.         |
| documento             | VARCHAR(20)  | NOT NULL, UNIQUE        | Número de documento o NIT.                          |
| telefono              | VARCHAR(20)  | NULL                    | Teléfono de contacto.                               |
| correo                | VARCHAR(100) | NULL                    | Correo electrónico de contacto.                     |
| direccion             | VARCHAR(150) | NULL                    | Dirección física.                                   |
| activo                | BOOLEAN      | NOT NULL DEFAULT TRUE   | Estado del cliente en el sistema.                   |

### Tabla: `categoria`

| **Campo**     | **Tipo**    | **Clave / Restricción** | **Descripción**                      |
| ------------- | ----------- | ----------------------- | ------------------------------------ |
| id\_categoria | INT         | PK, AUTO\_INCREMENT     | Identificador único de la categoría. |
| nombre        | VARCHAR(50) | NOT NULL, UNIQUE        | Nombre de la categoría de productos. |

### Tabla: `producto`

| **Campo**       | **Tipo**      | **Clave / Restricción** | **Descripción**                                |
| --------------- | ------------- | ----------------------- | ---------------------------------------------- |
| id\_producto    | INT           | PK, AUTO\_INCREMENT     | Identificador único del producto.              |
| id\_categoria   | INT           | FK → categoria          | Categoría a la que pertenece el producto.      |
| codigo          | VARCHAR(30)   | NOT NULL, UNIQUE        | SKU o código de barras (EAN).                  |

| unidad\_medida  | VARCHAR(20)   | NOT NULL                | Unidad (unid, cajas, bultos, tubos, etc.).     |
| precio\_compra  | DECIMAL(12,2) | NOT NULL DEFAULT 0      | Precio de adquisición (CHECK >= 0).            |
| precio\_venta   | DECIMAL(12,2) | NOT NULL                | Precio de venta sin IVA (CHECK >= 0).          |
| porcentaje\_iva | DECIMAL(5,2)  | NOT NULL DEFAULT 19.00  | Porcentaje de IVA aplicable (0 a 100).         |
| stock\_minimo   | DECIMAL(12,2) | NOT NULL DEFAULT 0      | Umbral para alertas de inventario bajo.        |
| existencias     | DECIMAL(12,2) | NOT NULL DEFAULT 0      | Cantidad disponible en stock (nunca negativa). |
| activo          | BOOLEAN       | NOT NULL DEFAULT TRUE   | Estado del producto en el catálogo.            |

### Tabla: `venta`

| **Campo**              | **Tipo**      | **Clave / Restricción**             | **Descripción**                                         |
| ---------------------- | ------------- | ----------------------------------- | ------------------------------------------------------- |
| id\_venta              | INT           | PK, AUTO\_INCREMENT                 | Identificador único de la venta.                        |

| tipo                     | ENUM          | NOT NULL                            | Tipo de movimiento (`entrada`, `venta`, `anulacion`, `ajuste`). |
| cantidad                 | DECIMAL(12,2) | NOT NULL                            | Cantidad con signo (+ o -).                                     |
| existencias\_resultantes | DECIMAL(12,2) | NOT NULL                            | Stock del producto tras aplicar el movimiento.                  |

## Conclusión

La arquitectura de datos de FerroGest concentra toda la información en una base de datos MySQL a la que acceden únicamente el backend y, a través de él, la interfaz y el asistente de IA. El diseño se derivó de los requisitos de la ERS y quedó en nueve tablas con historial de precios y de inventario, eliminación lógica y transacciones que garantizan la consistencia de las ventas y las existencias. Además, la estructura deja espacio para crecer con las mejoras previstas sin rehacer lo existente.
