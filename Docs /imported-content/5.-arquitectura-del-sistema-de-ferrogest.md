# 5. Arquitectura Del Sistema De FerroGest

Software para la gestión de ventas e inventario de ferreterías con asistente de IA

Ana Lucia Bermudez Rodríguez - Aldair Caicedo Ramos - Samuel Cuervo Rojas - Kevin Andres Puentes Mera

## Introducción

Hablaremos acerca de la arquitectura de sistema que se utilizará en FerroGest, un sistema de información web para la gestión de ventas e inventario de una ferretería, con un asistente conversacional con inteligencia artificial, primero se explica qué es una arquitectura de sistema, luego se comparan los tipos más comunes, por último, se describe la arquitectura elegida y se justifica esa decisión con las características del software.

## ¿Qué es una arquitectura de sistema?

La arquitectura de un sistema es una descripción breve y manejable de cómo se organiza el sistema y de qué manera interactúan sus componentes, como los sistemas con requisitos parecidos suelen resolverse con una arquitectura similar, esta también permite reutilizar soluciones que ya han funcionado en otros proyectos.

Elegir la arquitectura al comienzo del proyecto es importante porque condiciona cómo se construirá, se probará y se desplegará el sistema, y porque cambiarla más adelante es costoso. En una metodología en cascada, como la que sigue este proyecto, la decisión se toma antes de la implementación.

## Tipos de arquitectura

Se compararon tres opciones frecuentes para aplicaciones web:

| **Arquitectura**              | **Descripción**                                                                                                                                                                                              | **Ventajas**                                                                                                  | **Desventajas**                                                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Monolítica**                | Una única base de código y una única unidad de despliegue ejecutan todas las funciones del negocio, una variante es el monolito modular, que organiza ese código en módulos con responsabilidades separadas. | Sencilla de desarrollar, probar y desplegar, las transacciones son simples porque hay una sola base de datos. | Para escalar hay que escalar toda la aplicación, cualquier cambio obliga a desplegar todo, si no se ordena bien, el código se acopla. |
| **Cliente-servidor en capas** | El sistema se divide en un cliente que es la interfaz y un servidor que es la lógica y datos, el servidor suele organizarse en capas: presentación, lógica de negocio y acceso a datos.                      | Separa claramente las responsabilidades, el cliente y el servidor pueden evolucionar por separado.            | Depende de la red, exige definir bien cómo se comunican las partes.                                                                   |
| **Microservicios**            | El sistema se divide en servicios pequeños e independientes, cada uno con su propia lógica y, normalmente, su propia base de datos, que se comunican por la red.                                             | Cada servicio se escala y se despliega por separado, un fallo queda aislado en un servicio.                   | Mucha más complejidad operativa, las transacciones entre servicios son difíciles. Requiere más infraestructura y experiencia.         |

## Arquitectura elegida para FerroGest

FerroGest utilizará una arquitectura cliente-servidor en capas, con un backend monolítico modular. Es decir, la interfaz (frontend) está separada del servidor, y el servidor (backend) es una sola aplicación, con una única base de código y un único despliegue, organizada internamente en módulos y en capas.

Aunque hay que tener en cuenta que, en la arquitectura monolítica pura, la interfaz, la lógica del negocio y el acceso a los datos forman un solo bloque, en FerroGest lo monolítico es el backend, mientras que el frontend en React se mantiene como una aplicación aparte que se comunicara con él.

| **Componente**           | **Tecnología**                | **Responsabilidad**                                                                                                                                                                                                                                                                                 |
| ------------------------ | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Frontend (cliente)**   | React, en el navegador        | Muestra las pantallas, valida los formularios y se comunica con el backend, es la capa de vista.                                                                                                                                                                                                    |
| **Backend (servidor)**   | Node.js, con arquitectura MVC | Contiene la lógica del negocio, la autenticación, el control de acceso por rol y el acceso a los datos, está organizado en módulos como autenticación, usuarios, productos, inventario, clientes, ventas, dashboard y asistente de IA, y en tres capas: rutas y controladores, servicios y modelos. |
| **Base de datos**        | MySQL                         | Almacena toda la información del sistema y garantiza su consistencia mediante transacciones.                                                                                                                                                                                                        |
| **API del modelo de IA** | Servicio externo              | Redacta las respuestas del asistente a partir de los datos que le entrega el backend.                                                                                                                                                                                                               |

El funcionamiento general es el siguiente, el usuario accede desde el navegador, el frontend envía peticiones HTTPS con datos en formato JSON al backend, el backend valida el token de sesión y el rol, ejecuta la lógica del negocio y consulta MySQL, cuando el usuario escribe al asistente de IA, el backend obtiene primero los datos que el rol del usuario puede consultar y solo entonces envía esa información al modelo de IA para que redacte la respuesta.

## Justificación

{% stepper %}
{% step %}
### Tamaño del equipo y del plazo

El proyecto lo desarrollan cuatro personas en unas siete semanas, con metodología en cascada, una sola base de código es más fácil de coordinar, probar y entregar que varios servicios independientes.
{% endstep %}

{% step %}
### Carga pequeña

FerroGest está pensado para una ferretería, con unos 10 usuarios simultáneos, hasta 1.000 productos y unas 100 ventas diarias, no necesita escalar partes por separado, que es la principal ventaja de los microservicios.
{% endstep %}

{% step %}
### Consistencia de los datos

Registrar una venta y descontar el stock debe ocurrir como una sola operación, si una parte falla, no se guarda ninguna, con un solo backend y una sola base de datos, una transacción de MySQL lo resuelve de forma directa, con microservicios habría que coordinar varios servicios.
{% endstep %}

{% step %}
### Seguridad centralizada

El control de acceso por rol y la clave de la API de IA se manejan en un solo punto, el servidor.
{% endstep %}

{% step %}
### Compatibilidad con MVC

El monolito modular se organiza de forma natural en modelos, controladores y rutas, con React como capa de vista.
{% endstep %}

{% step %}
### Posibilidad de evolucionar

Al estar organizado por módulos, alguno de ellos podría separarse más adelante si la carga crece.
{% endstep %}
{% endstepper %}

## Ventajas y desventajas

### Ventajas

* Desarrollo y pruebas más rápidos, con una sola base de código.
* Transacciones simples y datos consistentes.
* Despliegue único y depuración más sencilla.
* Separación clara de responsabilidades entre interfaz, lógica y datos.

### Desventajas

* Para escalar hay que escalar todo el backend, no solo un módulo.
* Un error grave en el backend puede afectar a todos los módulos.
* Cualquier cambio obliga a volver a desplegar toda la aplicación.
* El asistente de IA depende de un servicio externo, si no está disponible, el sistema muestra un aviso y el resto de las funciones sigue operando.

## Conclusión

Para FerroGest se eligió una arquitectura cliente servidor en capas con un backend monolítico modular, porque es la que mejor equilibra la sencillez de construcción, la consistencia de los datos y el costo con las necesidades reales del proyecto, un equipo pequeño, un plazo corto y una carga moderada, además, permite aplicar el patrón MVC y deja abierta la posibilidad de evolucionar hacia una arquitectura más distribuida si el sistema crece.
