# 2. Especificacion de requisitos (IEEE830)

## 1. Introducción

En esta sección se presenta una visión general de la Especificación de Requisitos de Software (ERS) del sistema de información FerroGest, elaborada siguiendo la estructura del estándar IEEE 830. Consta de las siguientes subsecciones: propósito, ámbito del sistema, definiciones, acrónimos y abreviaturas, referencias y visión general del documento.

### Propósito

El propósito de este documento es especificar los requisitos funcionales y no funcionales del sistema FerroGest en su versión final implementada, una aplicación web para la gestión de ventas e inventario de una ferretería, que incluye un asistente conversacional con inteligencia artificial. Está dirigido al equipo de desarrollo y al docente de la asignatura como referencia formal del proyecto.

### Ámbito del sistema

**Nombre:** El sistema se llamará FerroGest.

#### Qué hará

* Gestionar usuarios y roles (administrador, vendedor y encargado de inventario), con control de acceso basado en el servidor y redirección en silencio ante accesos no autorizados.
* Administrar clientes, productos (con creación de categorías desde el formulario, definición de precios/IVA por administrador o encargado y stock inicial) e inventario (existencias y movimientos).
* Registrar ventas con valores en centavos, cálculo de totales, descuento automático de stock y generación de factura simulada en pantalla.
* Mostrar un panel de indicadores (dashboard) adaptado por rol, incluyendo métricas del periodo por valor vendido, productos críticos y movimientos recientes.
* Incorporar un asistente conversacional con IA ubicado en el dashboard, limitado a 5 tipos de consultas predefinidas y respetando los permisos de cada rol.

#### Qué no hará

FerroGest no incluirá contabilidad ni módulos financieros, nómina, compras a proveedores, facturación electrónica real ante la DIAN, pasarelas de pago ni tienda virtual para clientes.

#### Beneficios, objetivos y metas

El sistema busca reducir errores de registro y faltantes de inventario, y dar mayor visibilidad del negocio para decidir. Su objetivo general es desarrollar un sistema de información web para la gestión de ventas de una ferretería que permita administrar clientes, productos, inventario y ventas, e incorpore un asistente conversacional con IA que responda consultas sobre la información del negocio, para mejorar el control operativo y la toma de decisiones.

#### Documentos relacionados

Presentación del proyecto, formato de registro del equipo y el estándar IEEE 830.

## 2. Descripción general

### Perspectiva del producto

FerroGest es un sistema de información web que opera de manera independiente, aunque depende en cierta medida de un sistema externo: la API del modelo de IA que se usará en el chat conversacional. Los usuarios podrán acceder a FerroGest desde el navegador web, donde encontrarán la interfaz desarrollada en React, la lógica de los servicios en Node.js y la base de datos en MySQL.

### Funciones del producto

| Módulo           | Función                                                                                                                                                                              | Usuario que lo usará                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| Autenticación    | Permite a los usuarios iniciar y cerrar sesión de forma segura y recuperar su contraseña.                                                                                            | Todos                                            |
| Usuarios y roles | Permite al administrador crear, editar y desactivar usuarios y asignarles un rol; el sistema aplica los permisos de cada rol en todos los módulos.                                   | Administrador                                    |
| Productos        | Permite administrar el catálogo de productos de la ferretería como código, categoría, unidad de medida, precios y stock mínimo.                                                      | Administrador, encargado de inventario, vendedor |
| Inventario       | Permite consultar las existencias, registrar entradas, salidas y ajustes, revisar el historial de movimientos de cada producto y recibir alertas de stock bajo.                      | Administrador, encargado de inventario           |
| Clientes         | Permite registrar y administrar los datos de los clientes y consultar su historial de compras.                                                                                       | Vendedor, administrador                          |
| Ventas           | Permite registrar ventas y medio de pago, generar la factura simulada, descontar el stock automáticamente y anular ventas.                                                           | Administrador, vendedor                          |
| Dashboard        | Permite ver los principales datos del negocio, cuánto se vendió y productos en bajo stock según el rol.                                                                              | Administrador, encargado de inventario, vendedor |
| Asistente de IA  | Responde en lenguaje natural consultas sobre los datos del negocio, como stock bajo, ventas por periodo y productos más vendidos, limitando la información según el rol del usuario. | Todos                                            |

### Características de los usuarios

| Tipo de usuario         | Formación                                                                                          | Actividades                                                                                                                                                        |
| ----------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Administrador           | Dueño o gerente de la ferretería, no se exige formación técnica, pero sí conocimiento del negocio. | Gestionar usuarios y roles, administrar productos y precios, supervisar ventas e inventario, consultar el dashboard y usar el asistente de IA con acceso completo. |
| Vendedor                | Bachillerato, conoce el catálogo y atiende al cliente en el mostrador.                             | Registra ventas, atiende clientes, consulta existencias y utiliza el chat de IA dentro de sus permisos.                                                            |
| Encargado de inventario | Bachillerato o técnico, maneja bodega y existencias.                                               | Administra entradas, salidas, ajustes de stock, productos y supervisa el inventario crítico.                                                                       |

### Restricciones

* El frontend se desarrollará en React, el backend en JavaScript con Node.js y los datos se almacenarán en MySQL como base de datos.
* El backend debe seguir el patrón Modelo Vista Controlador (MVC).
* El desarrollo seguirá la metodología en cascada, con entregables documentales por fase.
* El equipo está conformado por cuatro personas con una dedicación aproximada de 10 horas semanales cada una, según el presupuesto.
* El asistente de IA depende de la API de un modelo externo, sujeta a su disponibilidad y a su costo por consulta.
* La facturación es simulada; no habrá integración con la DIAN ni con pasarelas de pago.
* La comunicación entre el frontend y el backend se hará mediante una API con HTTP/HTTPS con datos en formato JSON.
* El acceso estará protegido por autenticación con token y las contraseñas se guardarán con hash.
* El asistente de IA solo podrá consultar mediante funciones predefinidas y no deberá mostrar información fuera de los permisos del rol.

### Suposiciones y dependencias

* Los usuarios accederán a FerroGest desde un navegador web actualizado en cualquier sistema operativo.
* Los equipos de la ferretería tendrán conexión estable a internet.
* Los requisitos descritos en este documento se mantendrán estables durante la fase de implementación.
* Los datos iniciales del negocio serán dados por el personal de la ferretería.
* El asistente de IA depende de la API de un modelo externo, por lo que se asume que seguirá disponible, con condiciones y costos por token similares a los actuales.

### Requisitos futuros

A futuro se podrá implementar el tema de la cotización, permitiendo generar presupuestos para clientes y convertirlos en pedidos y facturas; el tema de los proveedores y compras, donde se podrán registrar; la facturación electrónica real integrada a la DIAN y una tienda virtual donde se puedan hacer pedidos en línea.

## 3. Requisitos específicos

Esta sección contiene los requisitos de FerroGest con el nivel de detalle necesario para que se pueda diseñar, construir y probar el sistema. Cada requisito tiene un código único: los requisitos funcionales se identifican como **RF-XXX-NN**, por ejemplo, RF-VEN-01; y los no funcionales como **RNF-XXX-NN**, por ejemplo, RNF-SEG-01, donde XXX indica el módulo o categoría y NN el número consecutivo.

### Interfaces externas

#### Interfaces de usuario

La interfaz de usuario de FerroGest es una aplicación web que se ejecuta en el navegador, diseñada para pantallas de computador de escritorio y portátil. Toda la interfaz está en español y los valores monetarios se muestran en pesos colombianos. Todas las pantallas, excepto el inicio de sesión, comparten la misma estructura:

* **Encabezado:** Nombre del sistema, nombre y rol del usuario autenticado, y botón para cerrar sesión.
* **Menú lateral:** Muestra únicamente los módulos a los que el rol del usuario tiene acceso.
* **Acceso al asistente de IA:** Botón visible en todo momento que abre un panel de chat en el módulo del dashboard.

#### Interfaces de hardware

Será necesario contar con un computador con capacidad para ejecutar un navegador web actualizado y conexión a internet.

#### Interfaces de software

* **Navegador web actualizado:** Chrome, Edge o Firefox.
* **Backend desarrollado en Node.js:** Se conecta a una base de datos MySQL y consume la API de un modelo de IA externo mediante peticiones HTTPS.

#### Interfaces de comunicación

El servidor y el navegador se comunicarán entre sí mediante protocolos de internet estándares HTTPS, los datos en formato JSON y el token será enviado en cada petición.

### Funciones

Los requisitos funcionales se organizan por módulo del sistema, lo que equivale a la organización por objetos que sugiere el estándar IEEE 830. Cada módulo corresponde a un conjunto de datos y funciones del negocio, coincide con la estructura del backend en MVC y con el reparto de trabajo del equipo. Los permisos por rol se resumen en la matriz del apéndice.

#### 3.2.1 Autenticación

**RF-AUT-01 Iniciar sesión:** El sistema permitirá a los usuarios iniciar sesión mediante correo electrónico y contraseña. Se asignará un token de sesión con una duración fija de 8 horas.

**RF-AUT-02 Cerrar sesión:** El sistema permitirá al usuario cerrar sesión manualmente en cualquier momento, invalidando el token de autenticación activo.

#### 3.2.2 Usuarios y roles

**RF-USR-01 Crear usuario:** El sistema permitirá al administrador registrar nuevos usuarios asignando nombre, correo, contraseña inicial y rol (administrador, vendedor o encargado de inventario).

**RF-USR-02 Editar usuario:** El sistema permitirá al administrador editar la información de los usuarios existentes (nombre, correo, rol y contraseña). El sistema impedirá que el administrador se quite a sí mismo su propio rol.

**RF-USR-03 Desactivar y reactivar usuarios:** El sistema permitirá al administrador desactivar y reactivar usuarios con confirmación previa. No se permitirá la autodesactivación de la cuenta en uso ni dejar el sistema sin administradores activos.

**RF-USR-04 Consultar usuarios:** El sistema permitirá al administrador consultar la lista paginada de usuarios registrados, incluyendo su rol, correo y estado actual.

**RF-USR-05 Control de acceso por rol:** El servidor verificará el rol del usuario en cada petición HTTP. En caso de intentar acceder a un módulo o recurso no autorizado, el sistema redirigirá en silencio sin mostrar mensajes de error explícitos.

#### 3.2.3 Productos

**RF-PRO-01 Crear productos:** El administrador y el encargado de inventario podrán registrar productos especificando código único, nombre, categoría —pudiendo crearse directamente desde el formulario—, unidad de medida, stock mínimo, precio de venta, porcentaje de IVA y stock inicial. Se permite la venta de productos con precio 0.

**RF-PRO-02 Editar productos:** El administrador podrá modificar todos los datos del producto. El encargado de inventario podrá editar los datos del producto excepto los precios de venta y el IVA.

**RF-PRO-03 Desactivar y reactivar productos:** El sistema permitirá tanto al administrador como al encargado de inventario desactivar y reactivar productos sin eliminarlos del historial.

**RF-PRO-04 Consultar catálogo de productos:** El sistema permitirá a todos los roles consultar el catálogo de productos con búsqueda por código o nombre. El vendedor no podrá visualizar el precio de compra.

#### 3.2.4 Inventario

**RF-INV-01 Consultar existencias:** El sistema permitirá a todos los roles consultar las existencias de mercancía en tiempo real, destacando visualmente aquellos productos con stock igual o inferior al mínimo.

**RF-INV-02 Registrar entradas de inventario:** El sistema permitirá al administrador y al encargado de inventario registrar entradas de mercancía sumando la cantidad al stock existente. El servidor no valida si el producto está desactivado al momento de ingresar la entrada.

**RF-INV-03 Registrar salidas y ajustes por conteo físico:** El sistema permitirá al administrador y al encargado de inventario registrar salidas —con motivo obligatorio— y ajustes por conteo físico indicando la existencia real contada. El sistema no permitirá que las existencias resultantes queden en valores negativos.

**RF-INV-04 Consultar historial de movimientos:** El sistema permitirá al administrador y al encargado de inventario consultar el historial de movimientos de un producto con filtros por rango de fechas y tipo de movimiento.

**RF-INV-05 Alertar stock bajo:** El sistema alertará en la interfaz y en el dashboard cuando un producto alcance un nivel de existencias igual o inferior a su stock mínimo definido.

#### 3.2.5 Clientes

**RF-CLI-01 Registrar clientes:** El sistema permitirá al vendedor y al administrador registrar clientes con su tipo, nombre o razón social, documento y teléfono.

**RF-CLI-02 Editar clientes:** El sistema permitirá al vendedor y al administrador actualizar los datos de contacto e identificación de un cliente registrado.

**RF-CLI-03 Consultar y buscar clientes:** El sistema permitirá al vendedor y al administrador buscar y consultar el listado paginado de clientes.

**RF-CLI-04 Consultar historial de compras de cliente:** El sistema permitirá únicamente al administrador consultar el historial de compras de un cliente y su saldo o acumulado total.

**RF-CLI-05 Desactivar y reactivar clientes:** El sistema permitirá al administrador desactivar y reactivar clientes. El cliente predefinido `'Consumidor final'` no podrá ser desactivado.

#### 3.2.6 Ventas

**RF-VEN-01 Registrar venta:** El sistema permitirá al vendedor y al administrador registrar una venta seleccionando un cliente y uno o más productos. El sistema descontará automáticamente el stock sin permitir existencias negativas.

**RF-VEN-02 Calcular totales de venta:** El sistema calculará automáticamente el subtotal, descuento e IVA por producto. Todos los importes monetarios se calcularán y almacenarán expresados con centavos, sin redondeo al peso.

**RF-VEN-03 Descontar stock:** El sistema descontará automáticamente el stock al confirmar la transacción, registrando el movimiento correspondiente del tipo venta.

**RF-VEN-04 Generar factura simulada en pantalla:** El sistema mostrará una factura simulada en pantalla tras la confirmación de la venta; no dispondrá de opción de descarga en archivo PDF.

**RF-VEN-05 Consultar historial de ventas:** El sistema permitirá consultar el historial de ventas registradas. El administrador visualizará la totalidad de las ventas y el vendedor únicamente las suyas.

**RF-VEN-06 Anular venta:** El sistema permitirá al administrador anular una venta registrada previa confirmación e indicando el motivo, reincorporando automáticamente las cantidades al inventario.

#### 3.2.7 Dashboard

**RF-DAS-01 Mostrar indicadores de ventas:** El sistema desplegará el valor total acumulado de las ventas realizadas en el día y en el mes actual.

**RF-DAS-02 Mostrar gráfica de ventas por periodo:** El sistema desplegará el gráfico con la tendencia de ventas diarias correspondiente a los últimos 7 o 30 días.

**RF-DAS-03 Mostrar productos más vendidos y stock bajo:** El sistema desplegará los 5 productos más vendidos del periodo seleccionable, calculados en función del valor total vendido, y el listado de productos en estado crítico de inventario.

**RF-DAS-04 Adaptar dashboard al rol:** El sistema adaptará la vista del dashboard según el rol: el administrador verá totales globales; el vendedor visualizará solo sus ventas; el encargado de inventario observará los últimos 10 movimientos de inventario y 8 productos críticos, sin métricas de ventas.

#### 3.2.8 Asistente de IA

**RF-IA-01 Recibir consultas en lenguaje natural:** El sistema incluirá el panel de chat con la IA de manera exclusiva dentro de la pantalla del Dashboard.

**RF-IA-02 Responder consultas predefinidas con datos reales:** El asistente de IA responderá estrictamente a 5 tipos de consultas predefinidas sobre los datos del negocio a través de funciones ejecutadas en el servidor.

**RF-IA-03 Respetar permisos de rol en el asistente:** El asistente de IA limitará sus respuestas y los datos entregados según los permisos del rol del usuario autenticado.

**RF-IA-04 Manejar consultas no soportadas y fallos de servicio:** El asistente informará al usuario de forma clara cuando una consulta no corresponda a las 5 preguntas soportadas o ante una eventual falla del servicio de IA.

**RF-IA-02 Responder consultas con datos reales**

El sistema deberá responder, con datos reales del sistema, al menos los siguientes tipos de consulta:

* Productos con stock bajo.
* Existencias de un producto.
* Ventas por periodo: hoy, semana o mes.
* Productos más vendidos.
* Historial de compras de un cliente.
* Ventas por vendedor, solo para administrador.

El servidor obtiene los datos mediante funciones predefinidas y el modelo de IA solo redacta la respuesta a partir de esos datos, sin inventar cifras.

Las respuestas se muestran en español.

**Prioridad:** esencial.

**RF-IA-03 Respetar los permisos del rol**

El sistema deberá limitar las respuestas del asistente a la información que el rol del usuario puede consultar.

* **Administrador:** Todas las consultas.
* **Vendedor:** Sus propias ventas, clientes y existencias.
* **Encargado de inventario:** Consultas de inventario.

Si el usuario solicita información fuera de su rol, el asistente responde que no tiene permiso y no entrega los datos. La verificación de permisos la hace el servidor antes de consultar los datos.

**Prioridad:** esencial.

**RF-IA-04 Manejar consultas no soportadas y fallos del servicio**

El sistema deberá informar al usuario cuando el asistente no pueda responder una consulta.

* Si la consulta no corresponde a ningún tipo soportado, el asistente informa qué tipos de consulta puede responder.
* Si el servicio de IA no está disponible, el sistema muestra un mensaje de indisponibilidad temporal y el resto de las funciones sigue operando.

**Prioridad:** condicional.

### Requisitos de rendimiento

FerroGest está pensado para una ferretería pequeña. La carga y el volumen de datos estimados son:

* El sistema deberá responder en menos de 5 segundos a las operaciones habituales con la carga estimada.
* El asistente deberá entregar su respuesta en menos de 15 segundos en condiciones normales, dado que depende de un servicio externo.
* El sistema deberá permitir que hasta 3 usuarios operen a la vez sin que se pierdan ni se dupliquen registros.

### Restricciones de diseño

* La arquitectura del backend seguirá el patrón MVC; la interfaz se implementará en React como capa de vista independiente que consume la API del backend.
* Los datos se almacenarán en una base de datos relacional MySQL, con transacciones para las operaciones que modifican varios registros.
* La comunicación entre el frontend y el backend se hará mediante una API sobre HTTP/HTTPS con datos en formato JSON.
* El asistente de IA accederá a los datos del negocio únicamente mediante funciones predefinidas del backend y no podrá ejecutar consultas libres sobre la base de datos.
* Los productos, clientes y usuarios no se eliminan; se desactivan, para conservar la integridad del historial.

### Atributos del sistema

#### Seguridad

* **RNF-SEG-01 Contraseñas:** Las contraseñas deberán tener mínimo 8 caracteres y almacenarse únicamente como hash, nunca en texto plano.
* **RNF-SEG-02 Sesión:** La sesión se identificará mediante un token que se envía en cada petición y que expira tras 8 horas de inactividad.
* **RNF-SEG-03 Control de acceso:** El servidor deberá verificar el rol del usuario en cada petición y rechazar las que no estén permitidas.
* **RNF-SEG-04 Comunicación cifrada:** En el entorno desplegado, toda la comunicación entre el navegador y el servidor deberá realizarse mediante HTTPS.
* **RNF-SEG-05 Clave de la API de IA:** La clave de acceso a la API del modelo de IA deberá guardarse solo en el servidor en las variables de entorno y no deberá ser visible en el navegador ni en el repositorio de código.
* **RNF-SEG-06 Validación de datos:** El servidor deberá validar los datos recibidos y usar consultas parametrizadas para prevenir la inyección SQL.
